# SECURITY & COMPLIANCE AUDIT — PropVault

**Audit Date:** 2026-11-18

---

## 1. Critical & High-Severity Findings

| ID | Severity | Location | Vulnerability / Defective Behavior | Required Remediation |
|---|---|---|---|---|
| **SEC-01** | **CRITICAL** | `backend/apps/properties/views.py` (`PropertyDetailView.get`) & `PropertySerializer` | **Unauthenticated Disclosure of Legal Title Deeds & Owner PII**: `PropertyDetailView` uses `AllowAny` for `GET` and serializes `documents` (direct links to Sale Deeds, Khasra, Tax receipts) and `owners` (nested `UserSerializer` containing owner full name, email address, and mobile phone number) to any anonymous caller. | Split `PropertySerializer` into `PublicPropertyDetailSerializer` (redacting exact street address, legal document file URLs, and owner email/phone) and `AuthorizedPropertyDetailSerializer` (accessible only to the property owner, assigned verifier/advocate, platform admin, or a buyer in an active `Transaction` for that property). |
| **SEC-02** | **HIGH** | `backend/apps/transactions/views.py` (`TransactionMilestoneView.post`) & `backend/apps/payments/views.py` (`PaymentListView.post`) | **Unverified Escrow Payment & Milestone Advancement**: Calling `POST /api/v1/transactions/<id>/milestone/` with `action: "PAY_TOKEN"`, `"PAY_ADVANCE"`, or `"COMPLETE_REGISTRY"` immediately creates a `Payment` record with `status = PaymentStatus.SUCCESS` and advances the transaction state without verifying any payment gateway signature or bank escrow UTR! Moreover, either buyer or seller can trigger any milestone action without role separation (e.g., a buyer could trigger `COMPLETE_REGISTRY` unilaterally). | 1. Enforce role-specific milestone permissions: only the Buyer can initiate payment orders; only verified Razorpay HMAC signatures or Admin/Escrow Officer UTR verification can mark a payment `SUCCESS` and advance `TOKEN_PAID` / `ADVANCE_PAID`; both Buyer and Seller (or assigned Advocate) must sign `AGREEMENT_DRAFTED`; only Admin/Advocate/Seller+Buyer confirmation with Sub-Registrar Deed Number can complete `COMPLETE_REGISTRY`. |
| **SEC-03** | **HIGH** | `backend/apps/accounts/views.py` (`RegisterView.post`) & `auth_service.py` | **OTP Code Returned in API Response (`dev_otp`)**: `AuthService.register_user` returns `dev_otp` in the response dictionary, and `RegisterView` includes `"dev_otp": result.get('dev_otp')` in the HTTP response body without checking `settings.DEBUG`. In production, an attacker could read the OTP directly from the JSON response. | Only include `dev_otp` when `settings.DEBUG is True`. Hash OTP codes at rest using `make_password` / SHA-256 and enforce attempt lockouts (`max_attempts = 5`). |
| **SEC-04** | **HIGH** | `backend/apps/verification/models.py` & `seed_indore.py` | **Unqualified Verification Badges**: Seeded properties and manual tier toggles mark properties as 100% `VERIFIED` without recording data provenance (`GOVERNMENT_VERIFIED`, `THIRD_PARTY_VERIFIED`, `PLATFORM_VERIFIED`, `USER_SUBMITTED`, `VERIFICATION_PENDING`, `UNABLE_TO_VERIFY`) or mandatory source references. | Add mandatory provenance fields to `VerificationItem` and `PropertyDocument`. Never display "Government Verified" unless backed by an authenticated government source record; display accurate provenance badges on every property and passport item. |
| **SEC-05** | **MEDIUM** | `backend/apps/properties/models.py`, `users/models.py`, `legal/models.py` | **Predictable Document Storage Paths & Missing Checksums**: Unlike `ListingMedia` (which uses randomized UUID keys and SHA-256 checksums), `PropertyDocument` (`properties/documents/%Y/%m/`), `KYCRecord` (`kyc/front/%Y/%m/`), `VerificationItem` (`verifications/evidence/%Y/%m/`), and `TitleSearchReport` (`legal/reports/%Y/%m/`) preserve client-supplied filenames and do not compute SHA-256 checksums. | Apply randomized UUID storage keys and SHA-256 checksum computation to all document and KYC file uploads. |
| **SEC-06** | **MEDIUM** | Platform-wide (`common/`) | **Missing Immutable Audit Trail (`AuditLog`)**: Privileged actions (KYC approval/rejection, role assignment, Property Passport tier verification, listing moderation, escrow milestone transitions) are logged only to stdout via `request_logging`, not persisted in an immutable database audit table. | Create an append-only `AuditLog` model in `common` (or `fraud`) recording `actor`, `action`, `target_type`, `target_id`, `ip_address`, `metadata_json`, and `created_at`, and hook it into all privileged services. |
| **SEC-07** | **MEDIUM** | `backend/apps/accounts/views.py` & `users/views.py` | **Missing Rate Limiting on Auth & OTP Endpoints**: While `listings` endpoints have `ScopedRateThrottle`, `/api/v1/auth/login/`, `/api/v1/auth/register/`, `/api/v1/auth/verify-otp/`, and `/api/v1/users/kyc/submit/` do not have throttle scopes attached. | Add `ScopedRateThrottle` (`auth_login: 10/min`, `auth_otp: 5/min`, `kyc_submit: 5/hour`) to all authentication and KYC endpoints. |

## 2. RBAC & ABAC Matrix Audit

| Stakeholder Role | Permitted Actions | Currently Enforced? | Required Fixes |
|---|---|---|---|
| **BUYER** | Browse listings, save searches/favorites, submit leads, book visits, make/counter/accept offers on others' properties, view own transaction room & pay escrow orders. | Mostly yes, except `PropertyDetailView` exposes private documents to everyone, and `TransactionMilestoneView` lets a buyer trigger seller/admin milestones. | Restrict `PropertyDocument` access to authorized transaction participants; enforce buyer vs. seller vs. admin milestone guards. |
| **SELLER / OWNER** | Create/edit own properties & listings, upload property documents, view leads/visits for own properties, counter/accept offers on own properties, co-sign agreements. | Yes on `Listing` and `Property` mutations (`IsOwner`). | Ensure sellers only see documents and transactions for properties they own. |
| **AGENT** | View/update assigned leads, coordinate assigned site visits, manage listings where authorized. | Partial (`LeadListCreateView` filters by `assigned_agent`). | Add `assigned_agent` access checks on `SiteVisit` and `Transaction`. |
| **ADVOCATE** | Access assigned property legal documents, submit `TitleSearchReport`, draft/review `LegalDeed`, verify `LEGAL` & `OWNERSHIP` passport tiers. | Partial (`TitleSearchReportListView` checks `Role.ADVOCATE`). | Restrict advocate document access to properties/transactions assigned for legal review. |
| **VERIFIER** | Inspect properties in verification queue, upload physical/financial verification evidence, update `PHYSICAL`/`IDENTITY`/`FINANCIAL` passport tiers. | Yes (`VerifyTierView` checks `HasRole(Role.ADMIN, Role.VERIFIER, Role.ADVOCATE)`). | Enforce provenance metadata (`verification_method`, `source_reference`, `authenticity_level`) on every tier update. |
| **BUILDER** | Manage own `BuilderProfile`, RERA projects, and project unit inventory. | No write endpoints exist yet. | Implement `IsBuilder` + object-ownership checks on `BuilderProfile`, `Project`, and `ProjectUnit`. |
| **ADMIN** | Moderate listings, review KYC, assign roles, oversee verification & fraud investigations, reconcile escrow payments, view audit logs. | Partial (Listing moderation & role assignment work; KYC review & fraud/audit log endpoints missing). | Add Admin KYC review, Escrow payment verification, and Audit Log oversight endpoints with mandatory `AuditLog` recording. |
